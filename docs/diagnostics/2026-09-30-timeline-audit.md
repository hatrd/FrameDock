## 结论

轻量 WinForms + mpv 预览 + FFmpeg 后台导出的方向可行。用户已经接受纯复制起点吸附到可复制位置，并未要求任意帧无损剪辑。本次失败是实现丢掉了首个关键帧，成品检查又没有识别出来，不是需求本身不可实现。

## 实现原因

1. `FrameDock/Exporter.cs:119` 在所有模式都拼接输入之后的 `-ss`；零起点也生成 `-i source -ss 0 -t 12.841 -c copy`。在本机 FFmpeg 与这份素材上，首个 DTS 为负的关键帧被丢弃，后续依赖帧不能作为片段开头，直到下一个关键帧才开始写入视频。
2. `FrameDock/MediaInfo.cs:135` 把负 DTS 截为 0；`FrameDock/MainForm.cs:434` 又把“DTS 减 5 毫秒”的结果截为 0。这使针对中间关键帧的提前寻址补偿在视频开头失效。负 DTS 是需要保留的信息，不能因为界面不显示负时间就清零。
3. `FrameDock/Exporter.cs:79` 的 VerifyAsync 只检查容器总时长、编码及轨道种类。调用真实验证器，用户的坏文件被接受为成功。音频填满时长，掩盖视频缺失。规格 SPEC.md 第 40 行明确要求核实实际起止范围，代码未做到。
4. 完成任务判重会再次调用同一验证器，所以坏文件还会被认定为既有成功产物，重复导出也不能自动纠正。

FFmpeg 的 [官方 -ss 文档](https://ffmpeg.org/ffmpeg.html#Main-options)区分输入端和输出端寻址，也说明复制模式会保留输入寻址点与所选位置之间的额外片段。命令位置、时间原点及包边界必须作为同一套规则验证。这里只证明了两个真实范围的对照结果，不把一个命令推广为所有格式的通用修复。

## 开发过程为什么没有拦住

原聊天记录表明，代理确实发现过“复制后视频晚约一秒开始”的症状，并尝试多种命令。但最终采取 DTS 提前 5 毫秒的补偿，没有建立包含零起点的回归门槛。原 Smoke 程序用固定 0.928/1.928 秒的寻址值测试 1–3 和 2–4 秒片段，绕过实际 UI 的首帧切点生成逻辑。

合成素材是 8 秒、每秒一个关键帧；用户素材的关键帧间隔约 8.333 秒。短 GOP 降低了失败的视觉严重程度，且未覆盖“第一关键帧有负 DTS”的关键条件。测试主要确认时长、编码和字幕画入，不能据此声称首尾范围正确。后续加强了判重和文件验证，但仍然复用了这个不足的成功标准。

原需求访谈在音轨、字幕、命名、托盘等细节上花了很多轮，而复制导出的时间语义没有先成为一个经过真实素材验证的技术小样。这是交付次序的问题，不是还需要向用户追问更多选项。

## 建议的修复与验收顺序

1. 先把纯复制和精确模式的命令及时间换算分开。保存原始 PTS/DTS 和 time_base，明确播放器相对时间与源时间戳的换算；避免统一套用输出端 -ss 和任意 5 毫秒补偿。
2. 零起点和中间关键帧分别做真实导出验证；覆盖 MP4/MKV、B 帧、长 GOP、非零起点、静音、短片段和可变帧率。不是现在要求增加这些产品功能，而是覆盖承诺支持的输入边界。
3. 成品验证检查首个可解码画面、视频覆盖区间、首尾音视频时间、关键帧保留和源范围对应关系。复制模式用包内容哈希验证内容；精确模式检查实际选帧与允许的编码差异。容器时长只是其中一项。
4. 对不满足验证规则的既有输出判为失败，不再以“存在且可读取”认定成功；保留用户文件，明确提示重新生成。
5. 才恢复 UI、队列和发布验证。此诊断没有实施通用修复，当前安装版仍有问题。

纯复制仍然需要接受关键帧和包边界限制。这里的正确对照片段容器时长为 12.900 秒，比所选 12.841 秒多约 59 毫秒；这与丢失 8.333 秒画面是不同级别、不同性质的问题。若要求任意起止帧完全一致，应使用精确模式。音频复制的时间粒度还取决于编码包，不等于音频采样间隔。

## 用户侧可改进的任务写法

用户已经提出关键帧限制及“预计范围 + 成品核实”，主责在实现方。以后可以把要求改成可验证的交付门槛：

> 先用我给的真实 MP4/MKV 做命令行小样，验证从第一帧和中间关键帧切片。给出实际首帧、末帧、音视频起止时间和源范围对应证据。纯复制不要求任意帧精确，但不允许丢掉起始 GOP、长时间无画面或音视频错位；无法保证就报失败。以上通过后再做 GUI、字幕和任务队列。完成说明必须区分已验证、未验证及暂不支持。

不必自行规定怎么处理 DTS，也不必增加更多选项；技术假设的验证是实现者的工作。让代理优先验证最可能使项目整体失效的条件，比增加访谈轮数更有效。
